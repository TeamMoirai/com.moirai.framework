# ConfigTable Service

> Luban configuration table bridge layer: the framework defines interfaces and a singleton entry point, while the specific configuration code is generated by Luban from Excel into the project assembly.

`ConfigTable` service on the Runtime side only contains the `ConfigTableService` static facade (`[HandlerHost]`) and the `ConfigTableServiceHandler` abstract contract: the former provides static entry points for the three capabilities the framework cares about (multilingual text, sprite loading, UI window paths), the latter defines the backend contract. The actual table data and the `Tables` collection are generated by the Luban export tool from templates into the project's `GameProto` assembly; the game-side `LubanHandler` (inheriting `ConfigTableServiceHandler`) is installed automatically via `RuntimeInitializeOnLoadMethod`, executing `ConfigTableService.Handler = new LubanHandler()`. The accompanying editor tools (`Tools/Settings/ConfigTableSettings` and `Tools/Config` menu) handle the generation, relocation, and table export of the configuration table project directory.

## Core Features

- Framework and config table decoupling: The framework only depends on the `ConfigTableServiceHandler` abstract contract; Luban-generated code lands in the business assembly, removing the config table does not affect compilation of other framework services
- Lazy loading `Tables`: `Tables` is loaded only on first access to `ConfigTableService.Tables`, automatically selecting binary (`ByteBuf`) or JSON (`JSONNode`) format based on the Loader return type in the generated code
- Editor-friendly: In non-play mode, `TextAsset` configuration is loaded directly via `AssetDatabase`, no need to start the resource system
- Multilingual bridging: Reads `LocalizedBean` fields from the generated code via reflection to register available languages, and expands `TbLocalizedStrings` into a `Dictionary<string, List<string>>` for use by the [Localization](Localization.md) service
- Sprite and UI configuration reading: `TbSprite` / `TbSpriteAtlas` / `TbUIWindow` tables drive sprite loading and window resource location
- Editor workflow: One-click copy of built-in Config template (including Luban executable, sample tables, generation templates), table export script invocation, and export path synchronization

## Core Types

| Class/Interface | Description |
|----------------|-------------|
| `Moirai.Atropos.ConfigTable.ConfigTableService` | Config table static facade (`[HandlerHost]`): `GetAllLocalizedStrings`, `LoadSpriteByID`, `GetUIWindowLocation`; forwards through the `Handler` property (fail-fast: lazily initialized when not ready, throws if the default factory is missing, never silently degrades) |
| `Moirai.Atropos.ConfigTable.ConfigTableServiceHandler` | Config table handler abstract base class (inherits `FrameworkHandler`) defining the backend contract; when no custom handler is installed, `DefaultConfigTableHandler` is used (logs errors and returns empty results) |
| `GameProto.Config.LubanHandler` | Game-side handler (inherits `ConfigTableServiceHandler`), auto-installed via `RuntimeInitializeOnLoadMethod`, bridging Luban-generated code and the framework facade |
| `GameProto.Config.Tables` | Luban-generated table collection (e.g., `TbLocalizedStrings`, `TbUIWindow`, `TbSprite`, `TbSpriteAtlas` and business tables) |
| `Moirai.Atropos.ConfigTable.Editor.ConfigTableSettings` | Editor settings (`FrameworkSettings`): config table root directory, data/code export paths |
| `Moirai.Atropos.ConfigTable.Editor.LubanTools` | Table export menu: `Tools/Config/Luban Export Table &X`, `Tools/Config/Open Table Directory` |

## Quick Start

```csharp
// Business code: directly access the generated Tables (lazy-loaded, reads tables on first access)
Tables tables = Tables.Instance;

// Read UI window configuration table (table example from built-in template)
if (tables.TbUIWindow.DataMap.TryGetValue("MainWindow", out var uiConfig))
{
    string prefabPath = uiConfig.DefaultRes;
}

// Framework-level API (forwarded via the ConfigTableService facade, no need to reference GameProto assembly)
// 1. Get all multilingual texts (called by Localization service on startup)
Dictionary<string, List<string>> localized = ConfigTableService.GetAllLocalizedStrings();

// 2. Load atlas sprite asynchronously by ID (TbSprite + TbSpriteAtlas cross-query)
Sprite icon = await ConfigTableService.LoadSpriteByID("icon_hero", cancellationToken: this.GetCancellationTokenOnDestroy());

// 3. Get UI window resource path
string location = ConfigTableService.GetUIWindowLocation("MainWindow");
```

## Configuration and Workflow

### Initial Generation

1. Open menu `Tools/Settings/ConfigTableSettings` (Config Table Settings)
2. Click "Generate Config to specified directory": copies the package's `Templates~/Config` (including `Excels` sample tables, `Luban` executable, `CustomTemplate` generation templates, `Defines`) to the selected directory; if the directory name does not contain "Config", a Config subdirectory is automatically created; if located within Assets, a `~` suffix is automatically appended to avoid Unity import
3. First-time use requires building the latest Luban with build-luban, or importing a pre-built Luban into the `[Luban]` folder of the config directory

### Daily Table Export

- Menu `Tools/Config/Luban Export Table` (menu item shortcut `Shift+X`) executes `gen_code_bin_to_project.bat` (`.sh` on OSX/Linux) in the config directory, generating data to `ClientDataOutPutPath` (default `Assets/AssetRaw/Default/Config/Table`) and code to `ClientCodeOutPutPath` (default `Assets/Scripts/GameProto`)
- Menu `Tools/Config/Open Table Directory` directly opens the config project
- After moving the config table directory, use "Redirect Config Directory" in the settings interface to re-specify it; after modifying export paths, click "Update Config Path" to automatically synchronize the keys in `path_export.conf` and the `CONFIG_PATH` constant in `CustomTemplate/ConfigTableService_Init.cs`

### Generated Outputs

| Output | Description |
|--------|-------------|
| Table code under `Gen/` | Individual table Beans and `Tables` collection |
| `LubanHandler.cs` | Game-side handler: implements the `ConfigTableServiceHandler` contract (multilingual parsing, Sprite/UI querying) and installs itself automatically |
| `ExternalTypeUtil.cs` | Luban extension type utility |

## Notes

- Generated code is table-export output; manual modifications will be overwritten on the next export. Custom logic should be written on the business side or by modifying the `CustomTemplate` templates
- Configuration data is packaged according to the PRELOAD preload tag. At runtime it is loaded via `ResourceService`; ensure the resource system is ready
- When no game-side handler is installed, `ConfigTableService.GetAllLocalizedStrings()` returns an empty result with an error logged by `DefaultConfigTableHandler`; the [Localization](Localization.md) service will fail to load as a result
- After modifying `m_ClientDataOutPutPath` / `m_ClientCodeOutPutPath`, you must manually execute "Update Config Path", otherwise `path_export.conf` still points to the old directory
- When the config root directory is located within Assets, a `~` suffix is automatically added (e.g., `Assets/Config~`); Unity will not import this directory, but the export script can still access it normally
